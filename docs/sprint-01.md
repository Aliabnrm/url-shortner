# اسپرینت ۱: پایهٔ قابل‌فهم و قابل‌آزمایش بکند

## هدف و معیار پایان

هدف این اسپرینت ساخت یک سرویس HTTP کوچک است که رفتار مشخصی دارد، تنظیمات اشتباه را زود تشخیص می‌دهد و می‌توان آن را تست و متوقف کرد.

معیارهای پذیرش:

- پروژه با TypeScript و pnpm اجرا و build شود.
- `GET /health` پاسخ `200` و JSON مشخص برگرداند.
- مسیر ناشناخته پاسخ `404` و خطای ساخت‌یافته برگرداند.
- خطای غیرمنتظره، پیش از ارسال پاسخ، به `500` تبدیل شود و جزئیات داخلی به مصرف‌کننده نرسد.
- تنظیمات نامعتبر قبل از بازکردن پورت رد شوند.
- با `SIGINT` یا `SIGTERM` پذیرش اتصال جدید متوقف شود و درخواست‌های فعال فرصت پایان داشته باشند.
- قالب‌بندی، بررسی نوع‌ها، تست‌ها و build موفق باشند.

ساخت لینک، دیتابیس، ورود کاربر و Redis در اسپرینت‌های بعدی اضافه می‌شوند.

## ۱. ابزارها چه نقشی دارند؟

**Node.js** محیط اجرای کد سمت سرور است. مرورگر برای اجرای این برنامه لازم نیست؛ برنامه روی دستگاه یا سرور اجرا می‌شود و درخواست شبکه می‌پذیرد.

**Express** ابزاری روی امکانات HTTP در Node.js است. کمک می‌کند مشخص کنیم برای ترکیب یک متد و مسیر، مثل `GET /health`، کدام تابع اجرا شود.

**TypeScript** پیش از اجرا ناسازگاری نوع‌ها را پیدا می‌کند. مثلاً `port` در تنظیمات نهایی یک عدد است. این موضوع خواندن و تغییر کد را مطمئن‌تر می‌کند، اما صحت دادهٔ واقعی محیط را تضمین نمی‌کند؛ برای آن اعتبارسنجی زمان اجرا داریم.

**pnpm** وابستگی‌ها را نصب و دستورهای تعریف‌شده در `package.json` را اجرا می‌کند. فایل lock نسخه‌های دقیق وابستگی‌ها، از جمله وابستگی‌های غیرمستقیم، را ثبت می‌کند. آن را همراه کد وارد Git می‌کنیم. نصب با `--frozen-lockfile` در صورت ناسازگاری package و lock شکست می‌خورد و بی‌صدا نسخه‌ها را تغییر نمی‌دهد.

**tsx** اجرای TypeScript در توسعه و تست را آسان می‌کند. در حالت `watch` پس از تغییر فایل، برنامه را دوباره اجرا می‌کند. بررسی نوع‌ها وظیفهٔ دستور مستقل `pnpm typecheck` است.

**Prettier** شکل نوشتن کد را یکدست می‌کند. پیدا کردن اشکال منطقی یا بررسی امنیت وظیفهٔ این ابزار نیست.

تنها وابستگی مستقیم زمان اجرای محصول Express است. TypeScript، ابزار تست و ابزار قالب‌بندی وابستگی توسعه‌اند.

## ۲. برنامه چگونه روشن می‌شود؟

با `pnpm dev` این اتفاق‌ها می‌افتد:

1. Node.js مقادیر `.env` را در صورت وجود در محیط فرایند قرار می‌دهد.
2. `src/server.ts` نقطهٔ ورود برنامه است.
3. `readConfig()` تنظیمات را می‌خواند و اعتبارسنجی می‌کند.
4. `createApp()` برنامهٔ Express و ترتیب اجزای آن را می‌سازد.
5. `app.listen()` روی آدرس و پورت مشخص منتظر اتصال می‌ماند.
6. پس از موفقیت اتصال، نشانی سرویس در ترمینال چاپ می‌شود.

**Port** یک شماره برای رساندن ترافیک به برنامهٔ مناسب روی یک دستگاه است. در `127.0.0.1:3000`، بخش اول دستگاه محلی و بخش دوم درگاه برنامه است.

اگر `PORT=hello` باشد، برنامه پیش از گوش‌دادن روی شبکه متوقف می‌شود. این تصمیم را **Fail Fast** می‌نامیم: مشکل تنظیمات را هنگام شروع و با پیام روشن تشخیص بده، تا بعداً به خطایی مبهم تبدیل نشود.

تمام مقادیر محیط ابتدا رشته‌اند. در `env.ts`، شکل رشتهٔ پورت بررسی و مقدارش به عدد تبدیل می‌شود. استفادهٔ مستقیم از `process.env` در تمام فایل‌ها باعث پراکنده‌شدن پیش‌فرض‌ها و قواعد می‌شود؛ فعلاً این مسئولیت یک محل مشخص دارد.

## ۳. چرا app و server جدا هستند؟

`app.ts` مشخص می‌کند برنامه با درخواست چه رفتاری داشته باشد. واردکردن این فایل به‌تنهایی پورت ثابتی اشغال نمی‌کند.

`server.ts` برنامه را اجرا می‌کند: تنظیمات می‌خواند، پورت باز می‌کند و سیگنال توقف را مدیریت می‌کند.

این جداسازی نمونه‌ای از **تفکیک مسئولیت‌ها** است. نتیجهٔ عملی آن در تست دیده می‌شود: Supertest برنامه را روی پورت موقت سیستم‌عامل امتحان می‌کند؛ لازم نیست سرور توسعه با پورت ۳۰۰۰ روشن باشد.

فعلاً تعداد مسئولیت‌ها کم است؛ برای همین پوشه‌های controller، service و repository نساخته‌ایم. وقتی ساخت و ذخیرهٔ لینک اضافه شد، بر اساس نیاز واقعی مرزهای بعدی را ایجاد می‌کنیم.

## ۴. یک درخواست چگونه پاسخ می‌گیرد؟

این دستور را اجرا کنید:

```bash
curl -i http://127.0.0.1:3000/health
```

`curl` نقش **Client** یا درخواست‌کننده را دارد. می‌تواند جای مرورگر، اپ موبایل یا سرویس دیگری قرار بگیرد. گزینهٔ `-i` سرآیندهای پاسخ را هم نمایش می‌دهد.

درخواست شامل متد `GET` و مسیر `/health` است. متد، قصد درخواست را بیان می‌کند؛ `GET` برای خواندن استفاده می‌شود. مسیر مشخص می‌کند درخواست دربارهٔ کدام منبع یا عملیات است.

در `app.ts` درخواست به اجزایی می‌رسد که به‌ترتیب ثبت شده‌اند:

```text
Client → Node HTTP server → Express app → healthRouter → HTTP response
```

`healthRouter` برای `GET /health` تابع دارد؛ پس پاسخ را می‌سازد:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: no-store

{"status":"ok"}
```

- **Status code** نتیجهٔ کلی درخواست را نشان می‌دهد؛ `200` یعنی موفقیت.
- **Header** اطلاعاتی دربارهٔ پاسخ است؛ `Content-Type` می‌گوید بدنه JSON است.
- **Body** دادهٔ اصلی پاسخ است؛ اینجا فقط وضعیت سلامت را داریم.
- `no-store` از ذخیره‌شدن این پاسخ در کش‌های سازگار جلوگیری می‌کند تا پاسخ سلامت قدیمی ذخیره نشود.

نام مسیر سلامت صرفاً قرارداد ماست. هیچ ویژگی جادویی در کلمهٔ `health` وجود ندارد. ابزار پایش هم می‌تواند همین مسیر را صدا بزند و وضعیت HTTP را بررسی کند.

این مسیر یک بررسی سادهٔ **Liveness** است: آیا سرویس HTTP پاسخ می‌دهد؟ بعداً **Readiness** را جدا بررسی می‌کنیم: آیا سرویس با وابستگی‌های لازم، مثلاً دیتابیس، آمادهٔ انجام کار است؟

## ۵. Middleware و ترتیب اجرا

Middleware تابعی در زنجیرهٔ پردازش درخواست است. می‌تواند پاسخ بدهد، درخواست را به مرحلهٔ بعد بفرستد یا خطا را منتقل کند.

در پروژه ترتیب چنین است:

1. مسیرهای برنامه فرصت پاسخ‌دادن دارند.
2. اگر هیچ مسیر یا متد ثبت‌شده‌ای پاسخ نداد، `notFoundHandler` پاسخ `404` می‌دهد.
3. اگر خطای پیش‌بینی‌نشده‌ای رخ دهد، `errorHandler` مسئول پاسخ خطاست.

اگر middleware مربوط به `404` را قبل از مسیرها بگذاریم، درخواست سلامت هم همان ابتدا `404` می‌گیرد. بنابراین ترتیب ثبت بخشی از رفتار برنامه است.

در Express، middleware معمولی با `next()` پردازش عادی را ادامه می‌دهد. `next(error)` پردازش را به مدیریت خطا می‌برد. در Express 5، خطای پرتاب‌شده از routeهای `async` نیز به مدیریت خطا منتقل می‌شود.

فعلاً endpoint ورودی JSON نداریم؛ به همین دلیل `express.json()` اضافه نشده است. هنگام ساخت API ایجاد لینک، پردازش بدنه، محدودیت اندازهٔ آن و مدیریت JSON نامعتبر را با هم اضافه می‌کنیم.

## ۶. خطای مصرف‌کننده و خطای سرور

برای `/missing` مسیر نداریم. پاسخ `404` است:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Route not found."
  }
}
```

`code` شناسه‌ای برای تصمیم‌گیری برنامهٔ مصرف‌کننده است؛ `message` توضیح انسانی است. مصرف‌کننده نباید مجبور باشد متن پیام را تجزیه کند تا نوع خطا را بفهمد.

اگر کد برنامه به خطایی پیش‌بینی‌نشده برسد، پاسخ `500` با کد `INTERNAL_SERVER_ERROR` برمی‌گردد. جزئیات در ترمینال سرور ثبت می‌شود، اما به کاربر پیام عمومی می‌دهیم. جزئیات ممکن است مسیر فایل، اطلاعات اتصال یا دادهٔ داخلی داشته باشد.

در تست، یک route آزمایشی خطا ایجاد می‌کند؛ چنین مسیری در محصول منتشر نشده است. تست بررسی می‌کند هم پاسخ عمومی بماند و هم خود خطا برای عیب‌یابی ثبت شود.

اگر بخشی از پاسخ قبلاً ارسال شده باشد، امکان ساخت یک پاسخ JSON جدید نداریم. شرط `res.headersSent` در این وضعیت خطا را به مدیریت پیش‌فرض Express می‌سپارد تا اتصال مطابق وضعیت خطا مدیریت شود.

## ۷. توقف صحیح سرور

`Ctrl+C` معمولاً سیگنال `SIGINT` می‌فرستد. ابزارهای مدیریت فرایند نیز برای توقف از `SIGTERM` استفاده می‌کنند.

برنامه در هر دو حالت `server.close()` را صدا می‌زند: پذیرش اتصال جدید متوقف می‌شود و اتصال‌های دارای درخواست فعال فرصت پایان می‌گیرند. برای جلوگیری از انتظار بی‌پایان، سقف ۱۰ ثانیه در نظر گرفته شده است. اگر مهلت تمام شود، اتصال‌های باقی‌مانده بسته می‌شوند و فرایند با کد ۱ خارج می‌شود.

به این رفتار **Graceful Shutdown** می‌گوییم. اهمیت آن بعداً با درخواست‌های نوشتن در دیتابیس روشن‌تر می‌شود؛ توقف ناگهانی می‌تواند کار در حال انجام را قطع کند. این سازوکار هم تضمین تکمیل تمام درخواست‌ها در هر شرایطی نیست؛ مهلت مشخص دارد.

## ۸. اجرای توسعه، بررسی نوع‌ها و build

- `pnpm dev`: بازخورد سریع هنگام تغییر کد.
- `pnpm typecheck`: بررسی کد برنامه و تست‌ها با قواعد سخت‌گیرانهٔ TypeScript، بدون ساخت خروجی.
- `pnpm build`: بررسی کد برنامه و تولید JavaScript در `dist/`.
- `pnpm start`: اجرای JavaScript ساخته‌شده با Node.js.

`tsconfig.build.json` تنظیمات پایه را به ارث می‌برد و فقط خروجی اجرایی را مشخص می‌کند. تست‌ها در پوشهٔ خروجی محصول قرار نمی‌گیرند. فایل‌های `.map` برای ارتباط خطای JavaScript با منبع TypeScript ساخته می‌شوند.

پروژه از ESM استفاده می‌کند؛ در `package.json` مقدار `type` برابر `module` است. پسوند `.js` در importهای داخلی برای سازگاری با خروجی قابل‌اجرای Node.js نوشته شده است؛ TypeScript هنگام بررسی، منبع `.ts` متناظر را پیدا می‌کند.

## ۹. تست‌ها چه اطمینانی می‌دهند؟

`tests/app.test.ts` رفتار HTTP را بررسی می‌کند: وضعیت پاسخ، نوع محتوا، قرارداد خطا، تفاوت متدها و پنهان‌ماندن جزئیات خطای داخلی. این‌ها تست یکپارچگی کوچک در مرز HTTP هستند.

`tests/env.test.ts` تابع تنظیمات را با ورودی‌های کنترل‌شده بررسی می‌کند. این تست‌ها واحدند و نیازی به روشن‌کردن سرور ندارند. آرگومان ورودی `readConfig()` باعث می‌شود تست بدون تغییر متغیرهای محیطی مشترک اجرا شود.

تست‌ها با test runner خود Node.js اجرا می‌شوند؛ Supertest کمک می‌کند درخواست HTTP بفرستیم و پاسخ را بررسی کنیم.

تست موفق به معنی اثبات نبودن تمام خطاها نیست؛ یعنی رفتارهایی که مشخص کرده‌ایم برای سناریوهای آزموده‌شده درست مانده‌اند. تست‌های فعلی جای آزمایش بار، امنیت، دیتابیس یا استقرار را نمی‌گیرند.

## ۱۰. تمرین‌های عملی

۱. سرور را روشن کنید و `/health` را در مرورگر باز کنید؛ سپس همان درخواست را با `curl -i` بفرستید. داده یکسان است، ولی curl سرآیند و وضعیت را هم واضح نشان می‌دهد.

۲. `/missing` را درخواست کنید و status، code و message را پیدا کنید.

۳. این درخواست را بفرستید:

```bash
curl -i -X POST http://127.0.0.1:3000/health
```

انتظار فعلی `404` است، چون route فقط برای GET ثبت شده است. سپس `curl -I http://127.0.0.1:3000/health` را امتحان کنید؛ HEAD فقط سرآیند برمی‌گرداند.

۴. سرور توسعه را متوقف کنید. در `.env` پورت را به `3001` تغییر دهید و دوباره اجرا کنید. درخواست را هم به پورت جدید بفرستید. آدرس بدون شمارهٔ پورت جدید به برنامهٔ قبلی وصل نمی‌شود.

۵. سرور را متوقف کنید و موقتاً `PORT=hello` بگذارید. اجرا باید با پیام مشخص شکست بخورد. مقدار را برگردانید. تغییر فایل محیط را با توقف و اجرای دوباره آزمایش کنید.

۶. در `health.ts` موقتاً مقدار `status` را تغییر دهید و `pnpm test` را اجرا کنید. شکست تست نشان می‌دهد قرارداد پاسخ تغییر کرده است. تغییر را برگردانید.

۷. نسخهٔ ساخته‌شده را با `pnpm build` و سپس `pnpm start` اجرا کنید. با `Ctrl+C` پیام بسته‌شدن سرور را ببینید و بررسی کنید درخواست بعدی دیگر پاسخ نمی‌گیرد.

۸. در پایان `pnpm check` را اجرا کنید. نتیجه باید موفق باشد.

پیش از اسپرینت بعد باید بتوانید توضیح بدهید چرا app از server جداست، چرا تنظیمات را در زمان اجرا اعتبارسنجی می‌کنیم، ترتیب middleware چه اثری دارد و تفاوت `404` با `500` چیست.
