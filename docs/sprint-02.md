# اسپرینت ۲: از URL اصلی تا لینک کوتاه و Redirect

## ۱. خروجی این مرحله

در این اسپرینت دو قابلیت داریم:

1. ارسال آدرس اصلی به `POST /api/urls` و دریافت لینک کوتاه.
2. بازکردن لینک کوتاه با `GET /:code` و انتقال به مقصد.

لینک‌ها فعلاً در حافظه ذخیره می‌شوند. هدف این مرحله شناخت جریان کامل درخواست، قرارداد HTTP، اعتبارسنجی، تولید شناسه و مدیریت خطاست. ذخیره‌سازی پایدار، مسئلهٔ مرحلهٔ بعد است.

## ۲. قرارداد API

### ساخت لینک

```http
POST /api/urls
Content-Type: application/json

{"url":"https://example.com/articles/backend?source=test#intro"}
```

پاسخ نمونه:

```http
HTTP/1.1 201 Created
Location: http://127.0.0.1:3000/aB3x9KpQ
Content-Type: application/json; charset=utf-8

{
  "shortCode": "aB3x9KpQ",
  "originalUrl": "https://example.com/articles/backend?source=test#intro",
  "shortUrl": "http://127.0.0.1:3000/aB3x9KpQ"
}
```

`201` یعنی یک منبع جدید ساخته شد. کد بالا نمونه است؛ کد واقعی به‌صورت تصادفی تولید می‌شود. `Location` در پاسخ ایجاد، نشانی منبع تازه را نشان می‌دهد؛ این پاسخ مثل `302` مرورگر را خودکار منتقل نمی‌کند.

ارسال دوبارهٔ یک مقصد، لزوماً همان لینک کوتاه قبلی را برنمی‌گرداند. در این مرحله هر درخواست ساخت می‌تواند یک لینک جدید ایجاد کند.

### بازکردن لینک

```http
GET /aB3x9KpQ
```

پاسخ:

```http
HTTP/1.1 302 Found
Location: https://example.com/articles/backend?source=test#intro
Cache-Control: no-store
```

سرور ما محتوای سایت مقصد را نمی‌خواند. مرورگر بعد از دریافت پاسخ، خودش به مقصد درخواست می‌فرستد. به همین دلیل اعتبار ساختار URL با موجود یا سالم‌بودن صفحهٔ مقصد فرق دارد.

`302` انتقال موقت است. `no-store` نیز ذخیره‌شدن این پاسخ در کش‌های سازگار را منع می‌کند. این تصمیم کمک می‌کند بازکردن لینک در مراجعات بعد هم از تصمیم فعلی سرویس پیروی کند. صرف انتخاب `302` به‌تنهایی جای سیاست کش را نمی‌گیرد.

## ۳. جریان ساخت لینک در کد

```text
POST /api/urls
  → بررسی Content-Type
  → خواندن JSON با محدودیت اندازه
  → اعتبارسنجی ورودی و استانداردسازی URL
  → تولید کد تصادفی
  → ثبت کد در Map، در صورت تکراری‌نبودن
  → ساخت shortUrl با مبدا تنظیم‌شده
  → پاسخ 201
```

در `src/routes/links.ts` کارهای HTTP انجام می‌شوند: دریافت درخواست، بررسی نوع محتوا، خواندن بدنه و ساخت پاسخ. بدنهٔ JSON حداکثر ۸ KiB، یعنی ۸۱۹۲ بایت، است. فشرده‌سازی ورودی را در این نسخه نمی‌پذیریم.

دادهٔ دریافت‌شده برای منطق برنامه از نوع `unknown` است. یعنی قبل از استفاده باید بفهمیم واقعاً چه ساختاری دارد. نوشتن یک interface در TypeScript، دادهٔ ارسالی کاربر را خودکار معتبر نمی‌کند.

در `src/links/validate-url.ts` این قواعد بررسی می‌شوند:

- ورودی یک object با فیلد رشته‌ای `url` باشد.
- رشته پس از حذف فاصلهٔ اطراف، خالی یا طولانی‌تر از ۲۰۴۸ نباشد.
- آدرس مطلق باشد و با `http://` یا `https://` شروع شود.
- داخل آدرس کاراکتر کنترلی مانند newline وجود نداشته باشد.
- نام کاربری یا رمز داخل URL وجود نداشته باشد.
- خروجی استانداردشده هم از حد طول محصول عبور نکند.

محدودیت ۲۰۴۸ تصمیم این محصول است؛ قانون عمومی HTTP یا همهٔ مرورگرها نیست. طول رشته با `length` جاوااسکریپت سنجیده می‌شود؛ محدودیت اندازهٔ کل بدنه برحسب بایت است.

`new URL()` ساختار URL را بررسی و استاندارد می‌کند. مثلاً `https://example.com` را به `https://example.com/` تبدیل می‌کند. مقدار استانداردشده را ذخیره می‌کنیم. این کار درخواست شبکه‌ای به مقصد نمی‌فرستد.

در `src/links/link-service.ts` منطق ساخت و پیداکردن لینک قرار دارد. این بخش پاسخ Express نمی‌سازد و به `req` یا `res` وابسته نیست.

## ۴. کد کوتاه چگونه ساخته می‌شود؟

```ts
randomBytes(6).toString('base64url');
```

از مولد تصادفی امن Node.js شش بایت می‌گیریم و با نمایش Base64URL به هشت کاراکتر تبدیل می‌کنیم. خروجی می‌تواند حروف کوچک و بزرگ، ارقام، `-` و `_` داشته باشد. این نمایش برای قسمت مسیر URL مناسب است.

این کار Hash کردن آدرس اصلی نیست؛ کد تصادفی تولید می‌کنیم و رابطهٔ آن با مقصد را نگه می‌داریم. کدها به بزرگی و کوچکی حروف حساس‌اند.

تصادفی‌بودن، یکتایی قطعی نیست. در هر تلاش، ذخیره‌ساز بررسی می‌کند کد قبلاً ثبت نشده باشد. اگر تکراری بود، کد جدید تولید می‌کنیم؛ پس از حداکثر ۱۰ تلاش ناموفق، پاسخ `503` می‌دهیم. درخواست در حلقهٔ بی‌نهایت نمی‌ماند و مقصد لینک قدیمی بازنویسی نمی‌شود.

## ۵. ذخیره‌ساز چه می‌کند؟

`src/links/link-store.ts` شامل نوع `Link` و کلاس `MemoryLinkStore` است. هر رکورد فقط دو داده دارد:

```ts
{
  (shortCode, originalUrl);
}
```

Map با `shortCode` کلیدگذاری شده و دو عملیات داریم:

- `insertIfAbsent`: اگر کد وجود ندارد، لینک را ثبت کن؛ در غیر این صورت شکست را اعلام کن.
- `find`: لینک ثبت‌شده را با کد پیدا کن.

بررسی و ثبت در این نسخه همگام‌اند و بین آن‌ها `await` نداریم. بنابراین در یک فرایند Node.js درخواست دیگری وسط این دو عملیات اجرا نمی‌شود. این ویژگی را نباید به دیتابیس یا چند فرایند تعمیم داد؛ آنجا به تضمین یکتایی در خود دیتابیس نیاز خواهیم داشت.

هر بار `createApp()` یک ذخیره‌ساز جدید می‌گیرد، پس تست‌ها دادهٔ یکدیگر را نمی‌بینند. ذخیره‌ساز و مولد کد را می‌توان هنگام ساخت app جایگزین کرد. این همان تزریق وابستگی در ساده‌ترین شکل است: چیزی که برنامه به آن نیاز دارد، از بیرون قابل‌تأمین است. برای آن ابزار یا چارچوب اضافه نصب نکرده‌ایم.

## ۶. مبدا عمومی با آدرس اجرای سرور فرق دارد

`HOST` و `PORT` می‌گویند سرور روی کدام رابط و پورت گوش بدهد. `PUBLIC_BASE_URL` می‌گوید کاربر لینک را با چه مبدا عمومی ببیند.

برای توسعه، اگر مقدار عمومی تعیین نشود، از آدرس و پورت محلی ساخته می‌شود. برای نمونه:

```dotenv
HOST=127.0.0.1
PORT=3000
# PUBLIC_BASE_URL=https://short.example.com
```

اگر بعدها پشت reverse proxy با دامنهٔ عمومی اجرا کنیم، می‌توان مبدا عمومی را صریح تنظیم کرد. مقدار باید فقط origin باشد، مانند `https://short.example.com`؛ مسیر اضافی، query، fragment یا اطلاعات ورود پذیرفته نمی‌شود. این گزینه به‌تنهایی دامنه، DNS یا HTTPS را راه‌اندازی نمی‌کند.

هدر `Host` درخواست مبنای ساخت لینک نیست؛ مصرف‌کنندهٔ API می‌تواند آن را تغییر دهد. تست داریم که حتی با Host متفاوت، خروجی از مبدا تنظیم‌شده ساخته شود.

## ۷. جریان Redirect و ترتیب مسیرها

```text
GET /:code
  → بررسی قالب کد
  → جستجو در Map
  → اگر موجود بود: 302 + Location + no-store
  → اگر موجود نبود: 404 + LINK_NOT_FOUND
```

ابتدا route سلامت ثبت می‌شود، سپس routeهای لینک، سپس middleware مربوط به مسیر ناموجود و در پایان مدیریت خطا. در نتیجه `/health` همچنان پاسخ سلامت می‌دهد.

قالب کد دقیقاً ۸ کاراکتر مجاز است. مسیر تک‌بخشی با این قالب، درخواست پیداکردن لینک محسوب می‌شود. کد ناموجود پاسخ `LINK_NOT_FOUND` می‌گیرد؛ مسیر دارای قالب دیگر، مثل `/missing`، پاسخ عمومی `NOT_FOUND` می‌گیرد. هر دو وضعیت HTTP برابر `404` دارند.

Express برای route نوع GET، درخواست HEAD را هم مدیریت می‌کند؛ در این حالت Redirect با سرآیندها و بدون بدنه برمی‌گردد. پاسخ جداگانهٔ `405` در این نسخه نداریم.

## ۸. خطاهای قابل‌انتظار و غیرمنتظره

`src/errors/app-error.ts` خطایی با سه ویژگی دارد: وضعیت HTTP، کد قابل‌پردازش و پیام انسانی. منطق برنامه می‌تواند چنین خطایی پرتاب کند و middleware مرکزی آن را به JSON تبدیل کند.

| اتفاق                                     | وضعیت | کد                       |
| ----------------------------------------- | ----- | ------------------------ |
| ورودی URL نامعتبر                         | 400   | `INVALID_INPUT`          |
| JSON خراب                                 | 400   | `INVALID_JSON`           |
| پارامتر مسیر با encoding خراب             | 400   | `INVALID_REQUEST`        |
| لینک پیدا نشد                             | 404   | `LINK_NOT_FOUND`         |
| بدنه بزرگ‌تر از ۸ KiB                     | 413   | `PAYLOAD_TOO_LARGE`      |
| نوع محتوا، charset یا compression نامناسب | 415   | `UNSUPPORTED_MEDIA_TYPE` |
| برخورد کد در تمام تلاش‌ها                 | 503   | `CODE_GENERATION_FAILED` |
| خطای پیش‌بینی‌نشده                        | 500   | `INTERNAL_SERVER_ERROR`  |

برای خطاهای parser هم پاسخ مشخص داریم؛ اشتباه ورودی کاربر به `500` تبدیل نمی‌شود. متن JSON خراب یا جزئیات خطای داخلی را در پاسخ بازتاب نمی‌دهیم. خطاهای غیرمنتظره همچنان در سرور ثبت و با پیام عمومی پاسخ داده می‌شوند.

## ۹. تست دستی، قدم‌به‌قدم

### اجرا

در ترمینال اول:

```bash
cd '/Users/a.abnar/Desktop/URL Shortner'
pnpm dev
```

پیش‌فرض مثال‌ها پورت ۳۰۰۰ است. اگر تنظیمات محلی متفاوت است، آدرس درخواست‌ها را تغییر دهید.

### ساخت لینک

در ترمینال دوم:

```bash
curl -i -X POST http://127.0.0.1:3000/api/urls \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com/?source=learning#intro"}'
```

باید `201`، فیلدهای `shortCode` و `originalUrl` و `shortUrl`، و سرآیند `Location` ببینید.

### بررسی انتقال

در دستور بعد، `PASTE_CODE_HERE` را با کد واقعی پاسخ بالا جایگزین کنید:

```bash
curl -i http://127.0.0.1:3000/PASTE_CODE_HERE
```

انتظار: `302` و `Location` دقیقاً برابر مقصد استانداردشده، شامل query و fragment. بدون `-L` فقط پاسخ سرویس خودمان را می‌بینید. مقدار `shortUrl` را در مرورگر باز کنید تا انتقال خودکار را هم مشاهده کنید؛ دسترسی به سایت مقصد به شبکهٔ شما وابسته است.

### ورودی نامعتبر و لینک ناموجود

```bash
curl -i -X POST http://127.0.0.1:3000/api/urls \
  -H 'Content-Type: application/json' \
  -d '{"url":"javascript:alert(1)"}'

curl -i -X POST http://127.0.0.1:3000/api/urls \
  -H 'Content-Type: application/json' \
  -d '{}'

curl -i http://127.0.0.1:3000/NoSuch01
```

دو درخواست اول باید `400 / INVALID_INPUT` بدهند. درخواست سوم، اگر کد ثبت نشده باشد، `404 / LINK_NOT_FOUND` می‌دهد.

### JSON خراب و نوع محتوای نادرست

```bash
curl -i -X POST http://127.0.0.1:3000/api/urls \
  -H 'Content-Type: application/json' \
  -d '{"url":'

curl -i -X POST http://127.0.0.1:3000/api/urls \
  -H 'Content-Type: text/plain' \
  -d 'https://example.com'
```

انتظار به‌ترتیب `400 / INVALID_JSON` و `415 / UNSUPPORTED_MEDIA_TYPE` است.

### بدنهٔ بزرگ

```bash
node -e "process.stdout.write(JSON.stringify({url: 'https://example.com/' + 'a'.repeat(9000)}))" | \
  curl -i -X POST http://127.0.0.1:3000/api/urls \
  -H 'Content-Type: application/json' \
  --data-binary @-
```

انتظار `413 / PAYLOAD_TOO_LARGE` است؛ محدودیت بدنه قبل از اعتبارسنجی فیلد URL اعمال می‌شود.

### آزمایش ناپایداری حافظه

۱. یک لینک بسازید و بررسی کنید باز می‌شود.

۲. در ترمینال اول `Ctrl+C` بزنید و دوباره `pnpm dev` را اجرا کنید.

۳. همان لینک کوتاه قبلی را درخواست کنید؛ انتظار `404 / LINK_NOT_FOUND` است.

این نتیجه محدودیت ذخیره‌سازی حافظه‌ای است. در حالت watch، تغییر کد هم برنامه را restart می‌کند و همین اثر را دارد. اکنون دلیل نیاز به دیتابیس پایدار را می‌توانیم عملاً ببینیم.

## ۱۰. تست‌های خودکار و معیار پایان

```bash
pnpm test
pnpm check
```

تست‌ها مسیر واقعی ساخت و انتقال، مقصد شامل query/fragment، تنظیمات مبدا عمومی، ورودی‌های نامعتبر، خطاهای parser، جدابودن حافظهٔ appها، حساسیت حروف، برخورد کد و درخواست‌های هم‌زمان را بررسی می‌کنند. تست‌ها سایت مقصد را باز نمی‌کنند؛ صحت `Location` را می‌سنجند.

برای تست برخورد، به‌جای تکیه بر شانس، مولد کد کنترل‌شده تزریق می‌کنیم. به‌این‌ترتیب مطمئن می‌شویم تکرار کد باعث تغییر مقصد قدیمی نمی‌شود و تلاش‌ها محدود می‌مانند.

معیار پایان: ساخت لینک `201` بدهد، لینک موجود `302` با مقصد درست بدهد، ورودی‌های اشتباه پاسخ مشخص بگیرند، لینک قدیمی با برخورد کد تغییر نکند و `pnpm check` موفق باشد.

محدودیت فعلی: داده‌ها به یک فرایند تعلق دارند، با توقف از بین می‌روند و با افزایش لینک‌ها حافظه بیشتری مصرف می‌کنند. گام بعدی PostgreSQL، migration، محدودیت `UNIQUE` و تست ماندگاری داده پس از restart است.
